# L0 强制层 · v1.0

> 装配图 §1 的 **L0**。规则不再只写在文件里——有闸门在模型之外拦。

---

## 为什么要有这一层

L1 常驻层（`常驻薄核.md`）做到的是**在场**：那段规则每条消息都在上下文里。
它做不到的是**有代价**：偏离时没有任何东西会把它打回来。

**判它守没守规矩的量具，不能是被判的那个模型自己。** 让 AI 自查有没有遵守规则，
等于让被考核者自己填表——这正是坑库 P1：*量具自身的错系统性偏向「更合格」*。

后果不是抽象的。`scaffold/规则台账.md` 有两栏：「触发过几次」和「哪条规则真的拦住过一次事故」。
在这一层存在之前，**这两栏在物理上永远填不了数**，因为没有任何东西会在规则被违反时记录。
而那份台账自己写的删除判据第一条就是「从未触发过」——它同时还写着：

> 一条从没报过警的规则，和一条根本没接上的规则，从外面看一模一样。

整套规则当时全在后一种状态。L0 是把它们接上。

## 五条闸

| 规则 ID | 事件 | 拦什么 | 拦不拦 |
|---|---|---|---|
| R-L0-001 | Stop | 回复第一行没有证据头 | **硬拦**，退回重写 |
| R-L0-002 | Stop | 红线短语（应该是/我记得/看起来…） | 只记账 + 提示 |
| R-L0-003 | PreToolUse | 改核心真源，而它不在任何 git 仓库下 | **硬拦** |
| R-L0-004 | PreToolUse | 不可逆命令（rm -rf / reset --hard / force push…） | **拦一次**，说明回滚路径后重发即放行 |
| R-L0-005 | SessionStart | 什么都不拦，注入开窗五步 + 真源路径 | — |

每条闸的「防的是什么」和「失效判据」写在 `config.json` 里对应条目的 `_prevents` / `_retire_when`。
⛔ 这两栏缺一不许入库——留空的意思是这条规则永远删不掉，那就是只增不减。

### 为什么 R-L0-002 只提示不拦

这些词在正常技术描述里也合法出现（「这个函数看起来是递归的」）。硬拦会逼出**规避性改写**——
把词换掉而不是把状态查掉。那是更坏的结果：**指纹没了，病还在**。

### 为什么 R-L0-004 第二次放行

第一次拦下不是为了禁止这类操作，是为了逼出一句「它做坏了拿什么还原」。
说出来了就该放行。⛔ 放行也记账，traces 里看得到「拦了但被确认执行」这一行。

## 装

```
python -X utf8 install.py
```

装机脚本会按平台挂好（Windows 走 `gate.ps1`，其余走 `gate.sh`），并把挂载状态列进自检表。
不想装：`install.py --no-hooks`（会明说跳过了什么）。

`settings.json` 是**你自己的文件**，所以装机只增不覆盖：

| 情形 | 行为 |
|---|---|
| 没有 settings.json | 创建，挂三个事件 |
| 有，但没挂过 L0 | **追加**，你原有的 hooks / permissions 一条不动 |
| 已经挂过 | 什么都不做（幂等） |
| 语法坏了 | **一个字节都不动**，出声让你先修——那文件里还有你的权限配置 |

改之前会留一份 `settings.json.before-l0`。

手工装（或换机器改路径）看 `settings.snippet.json`。

⛔ **判据逻辑一个字都不许写进 `settings.json`**。它是本机配置：没有版本、没有回滚点、换台机器就没了。
`settings.json` 只放路径。

## 关

改 `config.json` 的 `master_switch` 为 `false`，或单条闸的 `enabled` 为 `false`。

⛔ **关掉后每次回复会打一行提示。这是故意的。**
静默失效的闸门比没有闸门更贵——你会以为它在守着。这条规则本身就是薄核那句「兜底必须出声」。

## 读 traces

`traces/<日期>.jsonl`，一行一次触发：

```json
{"action":"block","rule":"R-L0-001","gate":"evidence","session":"...","count":1,"first_line":"..."}
{"action":"warn","rule":"R-L0-002","hits":["应该是","看起来"]}
{"action":"deny","rule":"R-L0-004","command":"rm -rf ...","pattern":"..."}
{"action":"pass_on_retry","rule":"R-L0-004","command":"rm -rf ..."}
{"action":"released","rule":"R-L0-001","count":3}
```

`action` 的五种值各自的意思：

| action | 含义 |
|---|---|
| `block` / `deny` | 真拦住了 → 填进规则台账「反向记录」表 |
| `warn` | 记了但没拦 |
| `pass_on_retry` | 拦过一次，人说明后确认执行 |
| `released` | **连续拦截到上限被迫放行** ← 这一行最值得看，它说明规则没起作用 |

`.state/` 下是每个 session 的计数，用于防死循环和 R-L0-004 的二次放行，可随时删。

### 一条命令看台账

```
powershell -NoProfile -File tally.ps1            # 全部
powershell -NoProfile -File tally.ps1 -Days 7    # 近 7 天
powershell -NoProfile -File tally.ps1 -Detail    # 逐条列出拦了什么
```

规则文本读 `config.json`，次数从流水现算。**这张表没有任何一格是手写的**——
`scaffold/规则台账.md` 那栏「触发过几次」正是靠它才第一次有真值。

⛔ 表里 `never fired` 有两种含义，从外面看一模一样：它防的事没发生过，
**或者它根本没接上**。别只凭这一栏删规则——先跑 `tests/hooks_gate_test.py` 排除第二种。
不拦只注入的闸（R-L0-005）会记一行 `inject`，就是为了让「接上了」这件事留下痕迹。

⛔ `RELEAS` 那一栏最值得看：它意味着闸门拦了、模型仍然没照做、这一轮被放过去了。
那些轮次按构造就是未经核实的。

## 闭环：它怎么变得更准

```
powershell -NoProfile -File loop.ps1            # 守护率 + 缺闸清单 + 哑闸清单
powershell -NoProfile -File loop.ps1 -All       # 全部缺口
powershell -NoProfile -File loop.ps1 -Guarded   # 已经有守的，和守它的是谁
```

**坑库每条的「失效判据」栏，写的就是「什么闸门能让这条坑结构性消失」。**
P7 的判据是「破坏性测试框架强制先断言破坏前后 sha 不同」，P22 是「取键一律走约定常量，
键不存在直接抛错」——那不是描述，是**规格说明书**。

坑库自己不知道哪些规格已经建成了，于是「已经守住的」和「还没人管的」躺在同一张表里，
长得一模一样。`pit_gate_map.json` 把这两类分开，`loop.ps1` 算出：

- **守护率** = 有守护者的坑 / 总坑数。**这个数只因「又建了一道闸」而涨，不因「又记了一条坑」而涨**——它量的是防住了多少，不是知道了多少。开窗时注入的就是它。
- **缺闸清单**，按这条坑**实际咬过几次**排序。把「68 条没守」（让人瘫痪）变成「这条咬过你 6 次，至今没东西守，而它的规格早就写好了」（能动手）。
- **哑闸清单**：有闸但零触发。先跑 `tests/hooks_gate_test.py` 排除「根本没接上」，再谈退休。

### 一次完整的循环长什么样

本窗真实发生过一次，全程记录在案：

1. `stress_a` 在全量回归里红了一次，单独重跑 8/8 全过，第二次全量也不复现 → **根因没查出来**
2. 查不出来的原因是 runner 只留末行，现场当场消失 → 记成坑库 **T18**
3. 按 T18 的防法改 `run_all.py`：判红那一刻就把当次完整输出落盘
4. 去 `pit_gate_map.json` 登记 T18 ← run_all.py
5. 守护率 21.8% → **22.7%**

⛔ 第 1 步没有被跳过。**那次红至今没查出根因**，坑库里如实写着。
从查不清里长出的机制，和从查清了里长出的机制，一样算数——但不许把前者说成后者。

## 已知限制（不许当成已验证）

| 项 | 状态 |
|---|---|
| `gate.ps1` 全部五条闸 | ✅ 本机实测，正反两面都造假验过（`tests/hooks_gate_test.py` 51 条判据） |
| 一键装的四种情形 | ✅ 全在沙盒里验过：全新／幂等／已有配置不被吃／坏 JSON 不动 |
| `gate.sh` | ⚠️ **未在真 POSIX 机器上实测**。只在 Windows 的 Git Bash 里过了 7 条，用的还是本机 python 而不是 jq。判据与 ps1 同源，但没跑过就是没跑过 |
| 证据头判据 | 只判**第一行的形状**，判不了内容真假。编一个证据头照样过闸——这是这条闸的天花板，不是 bug。坑库 W4 要求的是「实证自检」，离得还远，所以 W4 不算退休 |
| R-L0-003 | 只判「在不在 git 下」，不判「有没有 commit 过」，也不判工作区有没有未提交改动——**而坑库 R6 的核心恰恰是后者**。缺口已登记为 partial |
| R-L0-004 | 扫的是整条命令**文本**。把危险命令当字符串写在脚本里也会被拦（本窗真拦过一次）。这是有意的保守，用二次放行化解 |
| 守护率 | 22.7%（20/88）。它是个**下限**：只登记亲眼验证过的映射，宁可低报 |
| 进程开销 | 每次 Stop 和被匹配的 PreToolUse 启一个 PowerShell，约 200-300ms |

## 改这里之前

⛔ 闸门只绿过不算数。**造假让它红一次，才知道它真会拦。**

⛔ 每条「不许出现 X」的断言旁必须配一条反向断言（坑库 T13）——先证明取到的东西是真的。
本层两个 bug 都是被反向断言照出来的，正向断言全程绿着：

1. `[Console]::In.ReadToEnd()` 按 ANSI 解码 stdin，中文证据头变乱码 → **每一轮回复都被拦**。
   ASCII 用例全绿，只有「合法输入必须放行」那条照出来了。
2. `$ErrorActionPreference='Stop'` 把 git 的 stderr 当 terminating error → R-L0-003 在
   **它唯一要拦的场景**里 100% 放行，还打出「git not runnable」这种错误归因。
